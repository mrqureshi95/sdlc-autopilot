Skill Specification

SDLC Autopilot

SDLC Autopilot is an agent skill that turns a rough coding prompt into a risk-based engineering workflow: choose the right mode, make the smallest safe change, guard the root cause, test meaningful behavior, verify evidence, and disclose what AI-assisted review can and cannot prove.

Current model: Quick / Standard / Full Standard pipeline: 5 phases Core loop: Fix-Guard-Test-Verify Current branch: main Release target: skills.sh

Purpose

The skill exists to raise the default engineering discipline of AI coding agents. Its central promise is not that the AI becomes a professional auditor. Its promise is narrower and more useful: risk-classify the work, force evidence, prevent recurrence where practical, keep the source of truth intact, and make uncertainty visible before shipping.

What It Does

  • Selects Quick, Standard, or Full mode from risk and user intent.
  • Applies the Fix-Guard-Test-Verify loop to meaningful issues.
  • Biases toward TDD when a harness exists and the reproducer is cheap.
  • Preserves single source of truth, contract safety, and smallest safe change.
  • Runs an evidence-based Ready Gate before commit, push, PR, or deploy.
  • Loads deeper reference files only when the mode or phase requires them.
  • Separates script-enforced evidence from self-reported review claims.

What It Does Not Do

  • It does not prove full correctness.
  • It does not prove absence of vulnerabilities.
  • It is not a professional security audit, penetration test, or expert human review.
  • It does not auto-deploy.
  • It does not silently continue when verifier output contradicts self-assessment.
  • It does not override local style conventions for formatting.
  • It does not claim cross-agent pass rates without reproducible run artifacts.

When Not To Use The Full Workflow

SDLC Autopilot is meant to raise quality for real code, not bury every scratch experiment in lifecycle overhead. The current skill explicitly allows a lightweight path for disposable work while keeping risky domains protected.

Use Lightweight Discipline

For throwaway prototypes, spikes, scratch files, or quick experiments that will not be shipped, reused, deployed, connected to real data, or turned into production code, use Quick-style work and state that full lifecycle evidence was not produced.

Promote Immediately

If the work touches production code, real data, security, auth, payments, PII, crypto, deployment, database schema, shared contracts, or something the user wants to keep, promote to Standard or Full.

Skip For Explanations

Explanation-only questions do not need the lifecycle unless code or artifacts will be changed. The skill is a workflow for making changes, not a requirement for every technical conversation.

Mode Selection

Mode selection is risk-first. User wording can request more rigor, but it cannot downgrade high-risk work below its safe floor. Ambiguous risk defaults to Standard. Security, auth, payments, PII, crypto, deployment, database schema, and shared-library contract changes go to Full.

Condition Selected Mode Important Constraint
Security, auth, payments, PII, crypto, deployment, DB schema, or shared-library contract changes Full Never downgraded by words like just or quickly.
User explicitly asks for full, thorough, careful, or equivalent Full User can always request more rigor.
Bug fixes, features, validation, refactors, performance work Standard This is the default path for most real work.
Text, color, config, comments, docs, simple rename with no behavior impact Quick Promote immediately if behavior, tests, guardrails, multiple files, or risk appear.
Ambiguous risk Standard Use the safer middle path when risk is unclear.

Mode Specifications

These tabs document the current behavior in SKILL.md. Standard and Full treat engineering standards as non-negotiable. Quick applies them proportionally and promotes when the work is no longer trivial.

Quick Mode

Quick mode is for truly trivial, localized work: one-file, non-behavioral changes such as copy, color, comments, simple config, docs, or a simple rename with no behavior impact. It is designed to avoid ceremony while still preserving safety.

Entry Criteria

Low-risk, localized, no behavioral change, no risky domain, no required guardrail.

Required Flow

Read target file, make the smallest safe change, run available lint/tests, summarize in one line.

Hard Stop

Stop before commit, push, PR, or deploy and wait for user confirmation.

  1. Read the target file. The agent must understand the local context before editing.
  2. Make the smallest safe change. No speculative refactors.
  3. Run available checks. If no tooling exists, say so instead of pretending.
  4. Report concisely. Include the limitation note: AI-reviewed, not human-audited.
Promotion rule: Quick promotes immediately to Standard or Full if the work expands beyond one file, changes behavior, needs tests, needs a guardrail, or touches a risky domain.

Standard Mode

Standard mode is the normal workflow for bugs, features, validation, refactors, and performance work. It is a 5-phase pipeline built around focused context, TDD bias, full-diff verification, evidence at the Ready Gate, and explicit user confirmation before shipping.

  1. Understand. Clarify the request, explore relevant code and rules, then produce a brief plan with acceptance criteria, root-cause hypothesis for bugs, canonical sources of truth, edge-case matrix, and test strategy. Ask one focused question only if ambiguity remains.
  2. Implement. Warn and offer a branch if on main or master. Prefer a failing targeted test first when a harness exists. Follow project conventions, delegate domain-specific work to relevant installed skills, and keep scope tight.
  3. Verify. Run formatter/linter/type checks where available, run tests, apply Fix-Guard-Test-Verify to the original request, audit the full diff, close the edge-case matrix, and rerun the affected test scope.
  4. Ready Gate. Run scripts/verify-pipeline.sh standard when shell exists, load references/self-verification.md, resolve any contradiction with the script as authoritative, summarize evidence, and provide cross-model review where available or as a copyable prompt.
  5. Ship. Only after user confirmation, stage, commit, push, create a PR if requested, update changelog if used, and handle deployment through the deployment gate.

Full Mode

Full mode is Standard mode plus stricter controls. It is mandatory for high-risk domains and for explicit requests for full, thorough, or careful handling.

Before Implementation

Present the plan and wait for explicit approval before editing.

During Verification

Load references/deep-audit.md, run a deeper AI-assisted security pass, and add a convergence pass when audit findings exist.

Guardrails

Executable guardrails are mandatory for structural and security findings unless no executable guard is viable and the reason is explicit.

Summary

High-risk domains require the human-review recommendation in the final summary.

Full-mode deep audit scope

The deep audit reference covers OWASP-style AI review patterns, auth flow tracing, data handling, guardrail examples for common bug classes, API contract validation, database migration guidance, and the convergence protocol.

Expert Mode Overlay

Expert mode is not a fourth risk level. It is a presentation shortcut. When the user, repo instructions, or project guidance says expert mode, power mode, or I know what I'm doing, the agent reduces optional ceremony but keeps the same safety rules.

Still Required

  • TDD bias when practical.
  • Fix-Guard-Test-Verify.
  • Edge-case closure.
  • Guardrails.
  • Security review and honest disclosure.
  • Ready Gate and verification.

Reduced

Optional narration and presentation overhead. Expert mode keeps the work concise; it does not lower the risk floor.

Fix-Guard-Test-Verify

This is the core mechanism of the skill. It applies to the original request and every structural, behavioral, or security issue discovered during verification. Cosmetic work remains proportional.

Root-Cause Scan

The agent explains why the issue happened, searches for the same pattern elsewhere, reads every candidate in context, fixes only confirmed matches with the same risk and no existing guard, and caps automatic fixes at five.

Guard Priority

The preferred guard order is type/compiler rule, linter/static analysis, runtime assertion or invariant, targeted test, and code comment as a last resort.

Test Quality

Regression tests should satisfy inversion, behavior-over-implementation, negative or boundary coverage, and minimal mocking of only external I/O.

Verification

The Ready Gate uses two verification layers. The first is deterministic filesystem evidence from scripts/verify-pipeline.sh. The verifier now includes tracked, staged, and untracked files so brand-new files are not silently missed. The second layer is the agent's critical-outcomes self-check from references/self-verification.md. If they disagree, the script is authoritative.

Verifier Script Checks

  • Changes exist, including untracked files the agent just created.
  • Standard and Full require test-file evidence when source changes exist.
  • Detected tests run when a runner is available.
  • Coverage artifacts are checked when coverage tooling exists.
  • Executable guardrail signals are searched.
  • Added lines are scanned for hardcoded secrets and dangerous patterns.
  • Full mode checks for security-specific guardrail evidence.
  • Changed tests get an assertion-count signal.
  • Suppression and debug markers are flagged.
  • Strict inversion is optional with SDLC_STRICT_INVERSION=1.

Critical Outcomes

  • Scope clarity.
  • TDD happened or was concretely blocked.
  • Single source of truth and contract safety preserved.
  • Fix-Guard-Test-Verify evidenced.
  • Meaningful passing tests.
  • Edge cases closed.
  • Security review ran when required.
  • Script and self-check agree.
  • Limitations and human-review guidance are honest.
  • Deploy approval is explicit.

Trust Model

The skill does not treat all evidence equally. Some facts are checked by scripts against the filesystem. Other facts are review claims the agent must report honestly and reconcile against script output.

Script-Enforced Evidence

  • Tracked, staged, and untracked diffs.
  • Changed test-file evidence.
  • Supported test execution.
  • Coverage artifacts when present.
  • Executable guardrail patterns and assertion-count signals.
  • Added secrets, dangerous patterns, suppression markers, and debug markers.
  • Full-mode security pattern signals.
  • Optional strict inversion with SDLC_STRICT_INVERSION=1.

Self-Reported Evidence

  • Mode-selection rationale.
  • TDD timing and any blocker.
  • Root-cause scan scope and confirmed matches.
  • Single-source-of-truth and contract-safety reasoning.
  • Edge-case closure and unresolved risk.
  • AI-review limitation language and human-review recommendation.
  • Agreement or contradiction with the raw verifier output.

Incomplete Install Behavior

If an installed copy contains only SKILL.md, the agent cannot truthfully perform the documented Full-mode deep audit, Ready Gate self-check, deployment guidance, or script-enforced verification. The correct fix is to reinstall or copy the complete skills/sdlc-autopilot/ folder with references/ and scripts/.

AI Review Limits

The skill is intentionally honest about AI-assisted review. It can catch known patterns and common mistakes, but it cannot replace expert review for high-risk domains.

AI Review Can Help Catch

  • Known vulnerability patterns.
  • Obvious null or undefined bugs.
  • Common input-validation gaps.
  • Off-by-one mistakes.
  • Hardcoded secrets.
  • Familiar unsafe APIs such as raw dynamic evaluation or raw HTML insertion.

AI Review Cannot Reliably Catch

  • Novel attack paths.
  • Business-logic flaws.
  • Subtle distributed race conditions.
  • Cryptographic mistakes.
  • Supply-chain issues.
  • System-level risks outside the loaded context.
Required language: the skill forbids claims like security audit passed or professionally audited. Summaries should say AI-assisted review. For auth, payments, PII, crypto, medical, or legal work, the final summary must include: HUMAN REVIEW RECOMMENDED: This change touches [domain].
Full-mode standards map: references/deep-audit.md now asks agents to map high-risk findings to OWASP ASVS 5.0.0 areas and NIST SSDF groups: PO, PS, PW, or RV. This improves review discipline without claiming formal compliance or replacing expert assessment.

Evaluation Ecosystem

The repository includes fixture-based scenarios and partial machine-checking. The eval suite is outcome-focused: it checks whether the agent selects the right mode, adds guardrails, writes meaningful tests, handles risk, and discloses limitations. Public pass-rate claims require reproducible run artifacts rather than trust.

Manual Scenarios

evals/evals.json defines prompts, expected mode, fixture path, and human-verifiable assertions.

Fixture Validation

scripts/run-evals.sh validates JSON, fixture directories, recognized source files, and test-file presence where expected.

Artifact Harness

scripts/run-agent-evals.py applies patch.diff, runs the verifier, and evaluates optional machine checks.

Empirical Results

evals/empirical-results.md records current local evidence and the bar for future named-agent pass-rate claims.

Agent Metadata

evals/agent-run.schema.json supports agent name, version, surface, run time, and skill revision for reproducible campaigns.

Use Cases

Cosmetic or Docs Edit

Quick A single string, color, comment, or documentation-only change with no behavior impact.

Behavioral Bug Fix

Standard A search field hidden by mobile keyboard needs root-cause analysis, regression tests, guardrails, and diff review.

Feature Work

Standard A dark-mode toggle requires source-of-truth decisions, persistence, edge cases, accessibility, and tests.

Security Fix

Full Login SQL injection requires parameterized queries, root-cause scan, security guardrails, deep audit, and human-review warning.

Deployment Change

Full or Standard + Deploy Gate Deployment reference loads only when deploy is requested and still requires explicit approval.

Refactor or Contract Work

Standard or Full Shared-library contracts and DB schemas promote to Full; ordinary refactors use Standard with contract safety.

No-Tooling Project

Standard The workflow does not stop just because no runner exists; it writes logical tests and states verification limits.

Monorepo Fix

Standard Scans and tests are scoped to affected packages first, then broadened when risk requires it.

Expert Mode Request

Overlay The agent stays concise but still owes guardrails, edge closure, verification, and limitation disclosure.

Current Versus History

The current live workflow is the 5-phase Standard mode documented above. The changelog records that version 1.0.0 originally had a 7-phase standard pipeline, while the current unreleased state collapsed gate/test, audit, and regression/final verification into one Verify phase.

Current Behavior

Quick is a narrow trivial path. Standard is 5 phases. Full is Standard plus approval checkpoint, deep audit, convergence, and stronger guardrails.

Historical Note

The changelog's 1.0.0 section mentions the older 7-phase pipeline. This page treats that as history, not current behavior.
